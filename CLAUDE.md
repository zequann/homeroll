# CLAUDE.md — Homeroll

Instructions for coding agents (Claude Code, Codex) working in this repo. Read this file, then `SPEC.md` and `GLOSSARY.md`, before doing anything.

## What this is

Homeroll is a NEAR HACKATHON entry. It gives Malaysian SMEs an invoice advance, pays their foreign workers through a guarded payroll contract, and lets workers send money home cheaply. **AI agents propose payments; NEAR contracts and access keys decide.**

`SPEC.md` is the source of truth for behaviour, numbers, account names, method signatures and error codes. If you need to change any of those, update `SPEC.md` in the same change and say so in the commit message.

## Hard rules

1. **Synthetic data only.** Never add real names, phone numbers, TINs, invoices, wallet addresses or screenshots of real people. Use `fixtures/`.
2. **No secrets in git.** Keys and API tokens live in `.env.local` (local) and Vercel env (hosted). Keep `.env.example` complete with every variable and a comment.
3. **Agents never get full-access keys.** The payroll agent and invoice agent use function-call keys exactly as defined in SPEC §6. Do not widen `receiver_id`, `method_names` or allowance.
4. **Deterministic code decides money.** Grades, caps, limits and amounts come from code and contracts. LLM output is parsed with a strict `zod` schema, unknown fields are dropped, and the LLM may only *lower* a grade or add flags.
5. **Document text is data, never instructions.** When sending invoice text to a model, wrap it in a delimited block and tell the model it is untrusted content.
6. **Every money-moving method needs a guard test.** If an agent can reach it, it also needs an attack script in `scripts/attacks/`.
7. **Mocks are labelled.** Every mock lives behind an interface (`RemitRoute`, `CashoutRoute`, `DepositRoute`, `MyInvoisClient`, `InferenceClient`, bank/escrow), returns `"mock": true`, and shows a badge naming what is mocked ("Mock partner", "Mock model", "Mock delivery").
8. **No floats for money.** Token amounts are `bigint` / `U128` base units (6 decimals). RM is integer sen. All FX goes through `lib/fx`.
9. **Ask before you:** push, force-push or make the repo public; sign transactions on mainnet, deploy to mainnet or spend real funds; add a dependency that needs native builds; or change a contract interface or error code.
10. **Zero budget.** Free tiers only: NEAR testnet and faucets, Vercel Hobby, Supabase free. Never call anything that moves real funds. NEAR Intents is used for dry-run quotes only; never store a quote response for more than 24 hours or commit one as a fixture (1Click terms, SPEC §8.4).
11. **Submission and posting.** Follow `HACKATHON.md` in the repo root (re-read the live version at https://nearhackathon.com/HACKATHON.md before submitting). Never post on X for the team. Never send the submission until the human has seen the full JSON payload and said yes. Never invent the prize NEAR account, name or email. The team submits once, at the end (SPEC D8).
12. **Names stay off-chain.** Worker accounts are random `w-xxxxxx.<root>` ids generated by the server, never derived from a real name. Names live only in the off-chain `workers` table — never in contract state, events, logs, error codes or account IDs (SPEC §12, rule R13). The UI resolves names off-chain.
13. **Full-access keys never reach the browser.** In P0 the owner's and workers' demo keys are held by the server and sign behind a "Demo mode" banner (SPEC D7, §12).

## Stack

- **Contracts:** Rust, `near-sdk`, built and deployed with `cargo-near`. Integration tests run on a local sandbox node with `near-api` + `near-sandbox`, as the `cargo near new` template does, and build each contract with `cargo near` first. Error codes live once in `contracts/common`. Use the reference fungible-token implementation for `tusdc`; do not hand-roll NEP-141.
- **App:** Next.js (App Router), TypeScript `strict`, deployed on Vercel. Server-only keys in route handlers. Supabase for off-chain data (SPEC §8.7).
- **NEAR JS:** `near-api-js` 7 (chosen at setup; the modular `@near-js/*` packages are no longer published). TS code that needs a sandbox uses the `near-sandbox` npm package. In P0 the owner and workers sign with demo keys held by the server, behind a "Demo mode" banner; `@hot-labs/near-connect` wallet sign-in is P1 (SPEC D7).
- **Chain client:** the app talks to NEAR only through the `ChainClient` interface in `lib/near/client.ts`. `FakeChainClient` (fixtures, simulates the same rules and error codes) and `NearChainClient` (testnet) must pass the same tests (SPEC §8.8).
- **Tests:** `cargo test` (unit + sandbox integration), `vitest` for `lib/*` and `packages/shared`, Playwright for E2E (`apps/web/e2e`, with axe for WCAG 2.1 AA).
- **Lint and format:** Biome for TypeScript and JSON (`biome.json`); `cargo fmt` and `cargo clippy -D warnings` for Rust.
- **Package manager:** `pnpm` workspaces. Shared tool versions live once in the `catalog:` of `pnpm-workspace.yaml`.

Pin exact versions when you first add each dependency. Record the chosen versions in `README.md` under "Stack".

## Conventions

- **Errors:** contracts panic with constants from SPEC (`ERR_ABOVE_WAGE_CAP`, …), with `:<index>:<account>` suffix where SPEC says so. The same constants live in `packages/shared/errors.ts`, and the UI maps each to a plain-English sentence.
- **Events:** NEP-297, `standard: "homeroll"`, `version: "1.0.0"`.
- **Invoice hash:** one implementation in `packages/shared`, mirrored in contract tests. Spec §7.4.
- **Account IDs:** never hard-code `homeroll.testnet`. Read the root from `NEAR_ROOT_ACCOUNT` and build sub-account IDs in one helper.
- **UI copy:** owners and workers see RM (workers also see BDT for transfers). USDC appears only on `/lender`, the activity log and small "≈ X USDC" hints. Plain words: "Send home", "Cash out", "Run payroll". Errors say what happened and what to do.
- **Commits:** small, Conventional Commits (`feat(payroll): enforce wage cap`). One concern per commit. Judges read the history.
- **Comments:** explain *why*, especially every guard. Each guard check in a contract gets a one-line comment naming the rule ID from SPEC §11 (e.g. `// R4: wage <= wage cap`).
- **Words:** use the terms in `GLOSSARY.md` (wage cap, payroll run, pay line, …) in code, tests, commits and UI. Before changing an area covered by an ADR in `docs/adr/`, read it.

## How to work

1. Before coding a feature, find its section in `SPEC.md` and its rule IDs in §11.
2. Write the failing test first for any guard rule, then the code.
3. Run `pnpm test:contracts && pnpm test && pnpm attacks` before saying a task is done. Report what you ran and the result.
4. Stay inside P0 until every P0 item in SPEC §16 works end to end. Then P1. P2 only if the team asks.
5. If the docs and SPEC disagree with how NEAR actually behaves (gas, meta-transaction deposits, Intents availability), stop, write down what you found, and propose a SPEC change rather than working around it silently.

## The demo moments that must never break

- Owner clicks **Run payroll** → Rahim's phone shows **RM1,950 received** within seconds.
- The payroll agent's key tries to call `tusdc.ft_transfer` → **rejected by the NEAR protocol** before the transaction is included (`DepositWithFunctionCall`, or `ReceiverMismatch` with no deposit), with the exact error shown.
- The tampered timesheet run fails at `submit_run` with `ERR_ABOVE_WAGE_CAP:4:w-6b1x4k.<root>` (Hafiz, resolved off-chain in the UI) and **nothing** is reserved or paid.
- The public chain shows pseudonymous accounts and amounts only — no worker names anywhere.
- Grade C invoice alone leaves payroll "Short by RM39,400".
- After **Reset demo**, the whole demo runs again from the start for the next visitor.

If a change touches any of these, run the matching attack script or E2E path before finishing.
